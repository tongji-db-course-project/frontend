# POS 摄像头条码识别说明

## 1. 功能位置

- 页面：销售管理 → POS 收银
- 入口：`摄像头扫码`
- 相关实现：`src/views/sale/CheckoutView.vue`
- 条码识别库：`@zxing/browser@0.1.5`

本功能为纯前端扩展。摄像头画面和上传的条码图片仅在当前浏览器中处理，不上传到后端。识别得到条码字符串后，前端才调用现有商品查询接口。

## 2. 使用条件

浏览器只有在以下安全环境中才允许网页访问摄像头：

- 本地开发：`http://localhost`
- 部署环境：HTTPS

首次使用时需要允许浏览器摄像头权限。如果电脑连接了多个摄像头，可在浏览器地址栏旁的摄像头权限设置中切换设备，然后刷新页面。

当前支持的条码格式：

- Code 128
- EAN-13
- EAN-8
- UPC-A
- UPC-E

数据库种子数据中的 `690000000001` 等12位条码应按 **Code 128** 生成，不应按 EAN-13 生成。

## 3. 识别流程

系统同时使用多条识别链路，提高不同浏览器和摄像头下的兼容性：

1. 浏览器支持 `BarcodeDetector` 时，使用浏览器原生条码检测。
2. 使用 ZXing 持续扫描视频帧，并启用 `TRY_HARDER` 强力识别模式。
3. 每隔约900毫秒运行一次传统视觉定位和多尺度解码。
4. 用户也可以点击 `识别当前画面`，主动截取当前高清帧识别。
5. 摄像头无法稳定识别时，可以使用 `上传条码图片` 作为兜底。

## 4. 传统视觉框选与图像增强

传统视觉链路不依赖 YOLO 或其他模型，处理步骤如下：

1. 将摄像头帧缩小到最大640像素宽进行分析，降低主线程计算量。
2. 计算水平方向的灰度变化，寻找黑白竖向边缘密集区域。
3. 根据行、列边缘得分定位候选条码区域，并自动扩展边界。
4. 除视觉候选区外，同时尝试扫描框区域和完整画面，避免错误框选导致漏识别。
5. 为裁剪结果人工补充白色静区，减少深色背景对一维码解码的影响。
6. 依次尝试原图、2倍灰度对比度增强图、3倍黑白化图。

高分辨率画面只在定位阶段缩小；确定候选区域后会回到原始分辨率裁剪，尽量保留条纹细节。

## 5. 误读控制和商品查询

低分辨率或失焦画面可能将条码误读成其他数字。为避免错误商品进入购物车，实时扫描采用以下校验：

1. 同一结果需要在短时间内连续识别至少两次。
2. 前端使用识别结果调用现有商品列表接口。
3. 只有存在条码完全相同且状态为“在售”的商品时，才加入购物车并关闭摄像头。
4. 数据库中不存在的结果会被视为误读，页面继续扫描。

使用的后端能力仍是现有商品查询接口，不需要增加摄像头或图片上传接口。

## 6. 商品输入与收银草稿

除扫码外，商品输入框支持名称或条码联想查询。下拉选项会显示商品名称、条码、规格和售价，选择后直接加入购物车。

POS 草稿保存在当前标签页的 `sessionStorage` 中，包含：

- 购物车商品与数量
- 已选择会员及手机号
- 出库仓库
- 兑换积分

切换侧边栏页面或刷新后会恢复；关闭浏览器标签页后由浏览器清除。

## 7. 测试建议

推荐使用数据库中真实存在的条码测试，例如：

```text
690000000001
690000000002
690000000003
690000000004
690000000005
```

测试步骤：

1. 确认后端和数据库已启动，目标商品状态为“在售”。
2. 在条码生成器中选择 Code 128，并生成上述任一编码。
3. 打开 POS 收银页面并允许摄像头权限。
4. 保持条码横向、画面稳定、无明显反光，确保左右留白可见。
5. 验证识别后商品能够自动加入购物车。
6. 切换到其他页面再返回，验证购物车草稿仍然存在。

## 8. 已知限制

- 320×240 摄像头可用，但条码过小、失焦或反光时仍可能无法恢复已经丢失的条纹细节。
- 屏幕展示条码可能产生摩尔纹，打印条码通常更稳定。
- 摄像头权限、设备选择和实际分辨率由浏览器与操作系统共同决定。
- 如果部署页面不是 HTTPS，普通远程地址无法调用摄像头。
- 传统视觉算法用于辅助定位，不保证在复杂纹理背景中每次都准确，因此仍保留扫描框区域、完整画面和图片上传兜底。
